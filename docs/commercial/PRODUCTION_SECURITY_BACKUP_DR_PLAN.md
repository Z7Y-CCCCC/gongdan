# 工单系统生产安全、备份与灾难恢复计划书

版本：1.0
编制日期：2026-08-29
适用范围：`frontend`、`mobile`、`backend`、MySQL、Redis、上传附件、对象存储、Docker Compose 与 Windows 部署路径

**当前落地状态（2026-08-29）**

- 已在代码库实现：生产密钥防误提交、MySQL ROW binlog 基线、每日全量备份、5 分钟 binlog 归档、SHA-256 校验、独立 S3 备份桶 Versioning/Object Lock 门禁、异地复制、备份与归档监控、全量恢复演练、PITR 演练和受确认保护的真实恢复流程。
- 仍需在真实环境启用：创建专用 MySQL 备份/恢复账号，配置独立备份云账号和不可变桶，填写生产密钥，安装计划任务，执行首次全量备份和 PITR 演练并留存证据。
- 尚未完成的后续治理：附件桶跨账号复制和数据库/对象对账、集中密钥系统、主机暖备或高可用、供应链安全门禁、令牌存储改造及框架长期支持版本升级。
- 在真实数据库、对象存储和恢复主机完成演练前，本计划只能视为“能力已编码”，不能视为“灾难恢复已验收”。

## 1. 执行摘要

本系统已经具备生产化的部分基础：MySQL 逻辑备份、附件归档、SHA-256 校验、第二目录复制、备份新鲜度监控、受确认保护的恢复脚本、Windows 临时数据库恢复演练、健康检查和生产配置保护。但“有备份文件”不等于“发生事故后一定能恢复”。当前主要缺口是：

1. 数据库只有定时全量备份，没有经过验证的时间点恢复能力，按每日备份估算，最坏可能损失接近 24 小时数据。
2. 第二副本是普通可写副本，生产管理员账号或勒索软件仍可能同时删除、加密本地和 NAS 备份。
3. Docker 与 Windows 两条部署路径的备份、监控和恢复能力不一致。
4. 本地附件与数据库是顺序备份，不是同一一致性时间点，可能出现“数据库有记录但文件没有”或相反情况。
5. S3 模式下现有脚本明确跳过对象数据，实际保护依赖尚未落地的云端版本、复制和不可变策略。
6. 单机 Compose 或单机 Windows 部署存在主机、机房、网络和人工操作单点。
7. 当前 Java 8 + Spring Boot 2.7.18 已不在 Spring Boot 2.x 的开源支持期；如无有效商业支持，后续安全修复风险会持续上升。
8. CI 有测试和构建，但尚缺秘密扫描、依赖漏洞扫描、SBOM、容器扫描、制品签名和部署前安全门禁。
9. Web 登录令牌保存在 `localStorage`，一旦发生 XSS，令牌更容易被读取；Windows Nginx 的安全响应头也比 Docker 配置少。
10. 目前缺少覆盖勒索、误删、数据库损坏、主机丢失、云账号丢失、证书过期和关键人员不可用的完整应急手册。

本计划建议采用“分层恢复”目标：

- **基础生产目标**：核心业务 `RPO <= 15 分钟`，`RTO <= 2 小时`。
- **高可用目标**：核心业务 `RPO <= 5 分钟`，`RTO <= 60 分钟`。
- **备份原则**：执行 `3-2-1-1-0`，即至少 3 份数据、2 种介质、1 份异地、1 份离线或不可变、每次验证为 0 错误。
- **恢复原则**：先隔离和保全证据，再在干净环境恢复；未经校验的旧主机不得直接重新上线。

安全没有“一次做完”。计划完成后的关键产物不是更多脚本，而是每月都有证据证明：备份可读、数据可恢复、恢复时间达标、责任人找得到、备用账号和密钥能使用。

## 2. 系统现状与证据

### 2.1 架构和数据资产

| 资产 | 当前实现 | 恢复重要性 | 结论 |
| --- | --- | --- | --- |
| MySQL | MySQL 8.4，Docker 命名卷或 Windows MySQL 服务 | 最高 | 订单、库存、报工、用户、会话、通知、配置和审计的事实来源 |
| 上传附件 | 本地目录或 S3 兼容对象存储 | 高 | 必须与数据库元数据联合恢复并做一致性核对 |

## 3. 业务连续性目标

NIST 将 RPO 定义为事故后能够恢复到的时间点，将 RTO 定义为系统资源最长可不可用时间。本系统先采用以下可验收目标，业务增长后再升级：

| 等级 | 数据/能力 | RPO | RTO | 说明 |
| --- | --- | --- | --- | --- |
| A | 工单、库存、报工、用户权限、租户关系 | 15 分钟 | 2 小时 | 基础生产硬门槛 |
| A | 上传图片、附件 | 15 分钟 | 2 小时 | 与数据库一起验收，不能只恢复元数据 |
| B | 通知、内部聊天、用户偏好 | 1 小时 | 4 小时 | 仍需要备份，但可晚于核心交易恢复 |
| C | Redis 缓存 | 允许全部丢失 | 30 分钟内重建 | Redis 不作为灾备事实来源 |
| A | 安全审计和操作日志 | 5 分钟 | 4 小时内可查询 | 事故调查依赖，必须异机保存 |
| A | 源码、配置模板、迁移、应用制品 | 每次变更 | 1 小时 | 版本、哈希、SBOM 和恢复说明必须绑定 |

高可用客户或停机直接影响生产线时，将 A 级提升到 `RPO <= 5 分钟、RTO <= 60 分钟`，并采用托管 HA 数据库或双机复制、至少两个应用实例和自动流量切换。不能用“备份更多次”代替高可用架构。

## 4. 推荐目标架构

### 4.1 分区原则

1. **公网边界层**：CDN/WAF 或反向代理只暴露 443；证书自动续期；限制管理入口来源。
2. **应用层**：后端至少可运行两个无状态实例；会话继续以数据库哈希记录为准；附件不能依赖单个实例磁盘。
3. **数据层**：MySQL 和 Redis 不开放公网端口；应用账号、备份账号、复制账号、恢复账号分开授权。
4. **备份层**：生产主机只能写入新的备份对象，不能删除不可变历史；备份管理员与生产管理员使用不同 MFA 账号。
5. **管理层**：监控、日志、代码仓库、域名注册商和备份控制台均启用 MFA，保留独立的 break-glass 恢复方式。

### 4.2 两种落地档位

#### 推荐基础档：单活 + 暖备

适合中小工厂、预算有限但不能接受长时间停机：

- 一台生产主机，一台不同物理故障域的暖备主机。
- MySQL 主库 + 只读副本，或托管 MySQL 单主高可用服务。
- 附件使用 S3 兼容对象存储，不再使用单机本地目录作为最终存储。
- 每日全量备份 + 连续 binlog 归档到跨账号不可变对象存储。
- 暖备主机预装运行时和配置模板，不长期保存生产密钥；故障时从密钥系统注入。
- 外部健康检查和人工确认切换；目标 `RPO 15 分钟 / RTO 2 小时`。

#### 高可用档：多实例 + 托管数据层

适合生产线强依赖系统或多客户商业化运行：

- 两个及以上应用实例分布在不同可用区，由负载均衡器探活。
- 托管 MySQL Multi-AZ/高可用，自动故障转移并提供 PITR。
- 托管 Redis 高可用；即使 Redis 全丢，业务仍能从 MySQL 重建。
- S3 版本控制、Object Lock、跨账号和跨区域复制。
- 基础设施即代码，可在另一地区重建网络、应用、监控和权限。
- 预配置 DNS/流量切换与定期演练；目标 `RPO 5 分钟 / RTO 60 分钟`。

## 5. 备份方案

### 5.1 3-2-1-1-0 拓扑

每份关键数据应同时满足：

- **副本 1：生产数据**，用于在线服务。
- **副本 2：本地快速恢复备份**，用于普通误操作和短时故障，生产主机最多保留 7 天。
- **副本 3：异地不可变备份**，不同账号/站点，保留长期版本。
- 使用数据库存储与对象存储两种介质。
- 至少一份 Object Lock/WORM 或物理离线副本，生产管理员无权提前删除。
- 每份备份经过校验、实际恢复和业务级验证，最终记录必须为 0 未解释错误。

### 5.2 MySQL 备份

| 类型 | 频率 | 用途 | 默认保留 |
| --- | --- | --- | --- |
| binlog 连续归档 | 每 1-5 分钟上传一次或托管 PITR | 恢复到误删/污染前的具体时刻 | 35 天在线，视合规延长 |
| 每日逻辑全量 | 每日 02:00，低峰执行 | 跨版本核查、小规模恢复、表级提取 | 35 个日版本 |
| 每周物理全量/托管快照 | 每周 | 大库快速恢复，降低 RTO | 8 个周版本 |
| 月末不可变归档 | 每月 | 长期灾备、审计 | 12 个版本 |
| 年度归档 | 视合同/法规 | 长期留存 | 默认 3 个版本，须经数据保留政策批准 |
| 发布前备份 | 每次生产变更前 | 发布失败和迁移事故 | 至少保留到版本稳定 30 天 |

实施要求：

1. 明确开启并检查 `log_bin`、`binlog_format=ROW`、唯一 `server_id`、binlog 过期时间和归档延迟。
2. 全量备份必须记录数据库版本、GTID/binlog 文件及位置、Flyway 版本、应用版本、开始/结束时间和数据量。
3. 备份账号只具备完成备份所需权限；PITR 归档使用独立凭据，不能复用应用数据库密码。
4. 逻辑备份继续使用 `--single-transaction --routines --triggers`，同时补充 events、字符集、GTID 策略和错误日志检查。
5. 数据量增长后，不能只依赖 SQL dump。通过实测恢复时间决定何时切换到物理备份或托管快照。
6. 删除旧 binlog 前先验证已经异地归档；监控“最早可恢复时间”和“最后可恢复时间”。
7. 每次恢复先恢复到新数据库实例，验证完成后切流，禁止直接覆盖唯一生产库。

### 5.3 附件与对象存储

S3 是推荐生产模式，要求：

- 开启 Bucket Versioning。
- 开启 Object Lock；默认使用治理模式，监管要求高时评估合规模式。
- 使用独立备份账号/项目做跨账号复制；关键客户再增加跨区域复制。
- 服务端加密，密钥与备份分离管理；备份账号无权删除 KMS 密钥。
- 开启访问日志、对象清单、复制失败告警和生命周期策略。
- 每日生成“数据库附件记录 vs 对象清单”对账报告，分类处理缺对象、孤儿对象、大小/哈希不符。
- 每周随机恢复不少于 20 个对象并验证 MIME、大小、哈希和业务下载。
- S3 凭据优先使用短期角色凭证；必须使用长密钥时，限定桶、前缀和动作并定期轮换。

若暂时使用本地目录：

- 备份时进入短维护窗口，暂停新附件写入；先记录数据库时间点和文件清单，再生成附件快照。
- 附件备份必须复制到另一台设备和不可变异地存储，不能只放同一磁盘或长期在线的普通共享目录。
- manifest 记录每个文件的相对路径、大小和 SHA-256，而不只是 ZIP 整体哈希。
- 恢复后执行数据库/文件双向对账，再开放业务流量。

### 5.4 配置、密钥、日志和制品

- Git 保存 Compose、Nginx、Flyway、脚本和环境变量模板，但不保存真实 `.env`、私钥、短信/微信/S3 密钥。
- 真实密钥放入云 Secret Manager、Vault 或受 ACL/BitLocker 保护的本地密钥库，并保留离线加密应急副本。
- `.gitignore` 增加 `.env`、`.env.*`，再对白名单 `!.env*.example` 放行。
- 每次发布保存后端 JAR/镜像、前端包、移动端包、镜像 digest、Git commit、SBOM、签名和迁移范围。
- 日志实时发送到独立系统；应用管理员只能追加或查询，不能无痕修改历史审计。
- 日志默认保留 180 天，安全审计默认 365 天；最终期限由客户合同、隐私和法律要求决定。
- 备份 manifest 使用独立密钥签名，不能仅把 `.sha256` 与原文件放在同一可写目录。

### 5.5 备份加密和权限

1. 传输统一使用 TLS；NAS 使用受控 SMB/NFS 加密通道或 VPN。
2. 本地备份卷启用 BitLocker/LUKS；离线盘单独保管恢复密钥。
3. 云备份使用独立 KMS 密钥；密钥管理员与备份管理员分离。
4. 删除不可变备份、修改保留期、恢复生产库必须双人批准并记录工单。
5. 每季度复核生产、数据库、备份、域名、DNS、云账号和代码仓库权限。

## 6. 恢复与灾难处置剧本

所有事故先执行共同步骤：记录发现时间、暂停高风险自动化、隔离受影响资产、保全日志/快照、指定事故负责人、通过独立通讯渠道协作。只有在确认入侵入口已清除、密钥已轮换、恢复数据已验证后才能重新开放流量。

| 场景 | 首要动作 | 恢复方式 | 验收重点 |
| --- | --- | --- | --- |
| 错误发布 | 停止继续发布，保留当前数据库 | 回滚到兼容应用；有破坏性迁移时前滚修复或从隔离库提取数据 | 健康检查、核心冒烟、迁移版本一致 |
| 单表/单租户误删 | 立即记录误删时刻，避免扩大影响 | 备份 + binlog 恢复到临时库，仅提取受影响行，禁止整库倒退 | 工厂/租户边界、引用关系、审计记录 |
| 数据库损坏 | 隔离故障库，保留副本供调查 | 新建数据库，恢复最近全量并回放 binlog 到安全点 | 表数量、行数、约束、Flyway、关键业务汇总 |
| 附件误删 | 暂停生命周期和清理任务 | 从对象历史版本或不可变副本恢复指定对象 | 数据库元数据、文件哈希、下载与预览 |
| 生产主机损坏 | 不在故障盘上反复修复 | 在暖备/新主机按文档部署，注入密钥，恢复数据库和附件 | 全新主机可独立上线，旧主机不参与 |
| 机房断电/硬件故障 | UPS 安全停机，确认磁盘和 MySQL 状态 | 短故障用暖备；长故障迁移异地 | BIOS 自动上电、网络、DNS、实际 RTO |
| 勒索或入侵 | 立即断网隔离，不先删除证据 | 从可信时间点在干净环境重建；轮换所有密钥、账号和证书 | 不带回后门、备份时间早于入侵、审计完整 |
| 云账号/对象存储失陷 | 冻结高权限账号和复制规则 | 使用跨账号不可变副本和 break-glass 账号恢复 | 对方账号无法删除副本，KMS 密钥可用 |
| 区域/运营商故障 | 判断是否达到切换阈值 | 切到跨区域应用、数据库和对象副本，更新流量 | DNS TTL、复制延迟、第三方短信/微信可用性 |
| 证书或域名故障 | 从外部确认范围，保护注册商账号 | 续签/替换证书，使用备用 DNS 管理员 | 浏览器、API、移动端、回调地址全部验证 |
| 关键人员不可用 | 启用通讯录和双人替补机制 | 第二责任人按离线 runbook 和应急凭据操作 | 不依赖个人电脑、个人手机或个人云账号 |

### 6.1 恢复顺序

1. 网络、身份和密钥系统。
2. MySQL 新实例，并完成全量 + PITR。
3. 对象存储/本地附件，并完成双向对账。
4. 后端服务，以只读或维护模式启动。
5. Flyway 校验、缓存清空与重建。
6. 前端、移动端入口和第三方微信/短信能力。
7. 管理员登录、租户隔离、工单、报工、库存、通知、附件下载等核心流程。
8. 开放内部用户，再逐步开放外部流量。
9. 记录实际数据恢复点、实际恢复时间、缺失数据和后续补录方案。

### 6.2 恢复验收清单

- 备份签名、SHA-256、大小和 manifest 全部通过。
- 数据库版本、字符集、时区、Flyway schema history 与目标应用匹配。
- `factories`、用户、权限、工单、报工、入出库、库存和审计关键表计数合理。
- 随机抽查至少 5 个工厂/租户，证明查询和写入不会跨租户。
- 附件数据库记录与对象清单差异为 0，或每条差异都有批准的处置记录。
- 管理端和移动端均能登录、退出、强制下线和重新认证。
- 核心增删改查、审批、报工、库存变更和通知流程通过。
- 恢复环境没有沿用疑似泄露的密钥、会话和管理员密码。
- 外部监控、日志、告警、备份和下一轮 binlog 归档正常。
- 记录实际 RPO/RTO；不达标必须进入整改计划，不能口头关闭。

## 7. 安全与持续可用建设

### 7.1 身份和访问

- 超级管理员、运维、云账号、域名、代码仓库和备份平台全部启用 MFA。
- 应用管理员与系统运维管理员分权；日常账号不能直接执行恢复或删除备份。
- 数据库禁止公网访问，应用账号禁止 `DROP`、`GRANT` 等非业务权限。
- 管理员高风险操作要求重新认证、原因说明、审计记录和可选双人审批。
- 会话设置绝对有效期和空闲超时；密码、权限、设备异常或安全事故后能批量吊销。
- 将浏览器令牌从 `localStorage` 迁移到 HttpOnly Cookie 前，保持严格 CSP、短令牌寿命、XSS 自动测试和高风险操作二次认证。

### 7.2 主机、网络和应用

- 只开放 443；MySQL、Redis、Actuator 和后端内部端口仅允许受信网络访问。
- 操作系统启用自动安全更新窗口、EDR/防病毒、磁盘加密、时间同步和防火墙。
- RDP/SSH 通过 VPN、堡垒机或来源白名单，禁止直接暴露互联网。
- Docker 镜像固定到 digest，容器使用非 root 用户、只读根文件系统、资源限额和最小 capabilities。
- Nginx 两条部署路径统一安全头；确认所有子域 HTTPS 后再启用 HSTS，避免错误配置导致整站不可达。
- 文件上传校验扩展名、MIME、魔数、大小和存储路径；文件不在 Web 根目录执行，必要时增加恶意文件扫描。
- 插件接口和 iframe 采用来源白名单、最小权限、超时、限流、审计和版本签名，禁止插件任意访问内网地址。

### 7.3 软件供应链

现有 `.github/workflows/ci.yml` 已执行后端测试、前端测试/构建、移动端构建、Compose 配置验证和脚本语法检查，应追加：

1. Git 历史和 PR 的 secret scan。
2. Maven/npm 依赖漏洞和许可证扫描。
3. Java/TypeScript SAST 与关键 API 授权测试。
4. Dockerfile、Compose 和 Nginx 配置扫描。
5. 生成 CycloneDX 或 SPDX SBOM。
6. 容器镜像 CVE 扫描，Critical 阻断；High 按 SLA 管理。
7. 制品签名和来源证明，生产只允许部署受信签名。
8. 每月依赖升级窗口和紧急漏洞发布流程。

`backend/pom.xml:9,21` 当前为 Spring Boot 2.7.18 和 Java 8。Spring 官方已说明 2.7.18 是 Boot 2.x 开源支持终点，因此应在 90 天内完成迁移评估，并按阶段升级到当前受支持稳定线；若短期无法迁移，应购买仍有效的商业支持并明确到期日前的迁移截止日。

## 8. 监控、告警与值守

### 8.1 必须监控的信号

| 分类 | 指标/事件 | 建议告警阈值 |
| --- | --- | --- |
| 外部可用性 | Web、移动端、后端健康、关键登录/查询合成事务 | 连续 2-3 次失败告警 |
| MySQL | 可用性、连接池、复制延迟、磁盘、慢查询、锁等待 | 复制延迟 > 60 秒；磁盘 < 20% 或预计 7 天耗尽 |
| 备份 | 最新全量年龄、大小异常、签名、校验、binlog 归档延迟 | 全量 > 26 小时；归档延迟 > 10 分钟；大小偏离基线 30% |
| 恢复能力 | 最近一次恢复演练时间、RPO、RTO、失败原因 | 7 天无自动恢复测试或 30 天无业务恢复测试 |
| 对象存储 | 复制失败、版本/Object Lock、清单差异、KMS 状态 | 任一复制失败持续 15 分钟；对账存在未处理差异 |
| 主机/JVM | CPU、内存、磁盘 I/O、线程、GC、进程重启 | 按容量基线设阈值，避免只看是否存活 |
| 安全 | 异常登录、暴力尝试、权限变更、备份删除策略变更 | 高权限事件实时告警 |
| 证书/域名 | TLS 证书、DNS、域名到期时间 | 30/14/7 天分级提醒 |

### 8.2 告警规则

- 告警必须发送到不依赖生产系统的渠道，并有短信/电话升级路径。
- P0 告警 10 分钟无人确认则自动升级到第二责任人；30 分钟升级负责人。
- 告警信息包含时间、环境、工厂/租户范围、症状、最近变更、runbook 链接和当前责任人。
- 每月统计误报、漏报、确认时间和恢复时间，淘汰长期无人处理的“背景噪声”。

- **SEV-3**：局部功能降级、非核心第三方故障、备份一次失败但仍有可用恢复点。工作时段处理并跟踪。

## 11. 90 天实施路线图

### 阶段 0：决策与冻结基线，1-3 天

- 业务负责人批准 RPO/RTO、部署档位、预算和责任人。
- 盘点所有生产账号、域名、证书、数据库、对象桶、主机、NAS、第三方和真实数据位置。
- 在任何改造前执行一次全量备份并复制到离线介质，记录当前可恢复点。
- 输出网络图、数据流图、账号权限表和资产清单。

**出口条件**：不知道由谁管理、放在哪里、何时到期的关键资产数量为 0。

### 阶段 1：备份保命线，4-14 天

- 落地异地对象存储，开启版本控制、加密、Object Lock 和独立账号。
- Docker 和 Windows 都将数据库/附件备份上传到不可变存储。
- 启用 binlog 连续归档并监控归档延迟。
- 给 manifest 加独立签名；增加备份年龄、大小、签名、磁盘和失败告警。
- 修正 `.env` 忽略规则，启用秘密扫描并轮换任何历史暴露凭据。
- 完成一次全量 + PITR + 附件的隔离恢复演练。

**出口条件**：能恢复到指定 15 分钟窗口，且生产管理员无法删除不可变副本。

### 阶段 2：安全加固与可观测性，15-30 天

- 统一 HTTPS、Nginx 安全头、网络边界、数据库/Redis 私网和管理员 MFA。
- 集中日志，补齐外部合成监控、证书/DNS、数据库与对象复制告警。
- CI 增加秘密、依赖、SAST、容器扫描、SBOM 和制品签名。
- 完成高权限、数据库、备份和云账号最小权限改造。
- 完成插件安全边界和上传文件安全评审。

**出口条件**：SEV-1 风险均有技术控制、告警、责任人和运行手册。

### 阶段 3：持续可用与暖备，31-60 天

- 建立暖备或多实例应用环境，移除本地附件单点。
- 配置数据库复制/托管 HA 和明确的人工或自动切换标准。
- 用基础设施脚本从空白主机重建环境。
- 完成主机完全损坏演练和 DNS/流量切换演练。

**出口条件**：在不使用原生产主机的情况下，2 小时内恢复核心业务。

### 阶段 4：长期治理，61-90 天

- 完成 Java/Spring Boot 升级方案、兼容性测试和分批迁移排期。
- 建立漏洞 SLA、月度补丁、季度权限复核、年度渗透测试。
- 完成数据分类、保留/删除、隐私与事件通知政策。
- 完成季度勒索演练和首份管理层韧性报告。

**出口条件**：所有控制均有负责人、周期、证据位置、最近执行时间和下次执行时间。

## 12. 上线硬门槛

以下任一项未满足，系统不得以“正式生产且可承担关键业务”的名义上线：

- 最近 24 小时内有成功的数据库全量备份，最近 15 分钟内有连续 binlog 恢复点。
- 数据库和附件至少各有一份异地不可变副本。
- 最近 30 天完成一次完整业务恢复，实际 RPO/RTO 达标。
- 生产、云、备份、域名、代码仓库高权限账号均启用 MFA 并有第二责任人。
- 真实密钥没有进入 Git、镜像、前端包、日志或普通备份 manifest。
- MySQL、Redis、Actuator 和后端内部端口没有直接暴露公网。
- TLS、证书自动续期、外部监控和告警升级链路已验证。
- 生产部署使用可追溯、经过扫描和签名的版本；Flyway 校验通过。
- 恢复 runbook 有离线副本，break-glass 凭据已实际验证。
- SEV-1 联系人、客户沟通模板、供应商支持入口和法律/监管联络路径明确。

3. `P0-Object-01`：S3 版本、Object Lock、复制、清单、对账和抽样恢复。
4. `P0-Monitor-01`：统一监控备份、PITR、磁盘、数据库、对象复制、证书和外部入口。
5. `P0-Drill-01`：全新隔离环境一键恢复与业务验收脚本。
6. `P0-Secret-01`：`.env` 防误提交、秘密扫描、密钥盘点与轮换。
7. `P1-Identity-01`：管理员 MFA、高风险再认证和 Web 会话 Cookie 化设计。
8. `P1-SupplyChain-01`：SCA/SAST/SBOM/镜像扫描和制品签名。
9. `P1-HA-01`：暖备主机、数据库复制和附件外置。
10. `P2-Upgrade-01`：Java LTS 与受支持 Spring Boot 版本升级。

每个任务的完成定义都必须包含：代码/配置、自动测试、回滚或前滚方案、运行手册、监控、演练证据和责任人。只提交代码而没有恢复验证，不算完成。

## 17. 需要管理层确认的四个决定

1. 采用“单活 + 暖备”还是“多实例 + 托管 HA”档位。
2. 是否批准核心业务 `RPO 15 分钟 / RTO 2 小时`；若不能接受，应升级到高可用档。
3. 不可变备份使用哪个独立云账号/对象存储，以及保留期限和年度预算。
4. 谁担任业务、恢复、安全、沟通四类负责人及替补，并授权季度停机演练窗口。

四项确认后，才能把本计划转为具体任务、采购清单、配置变更和演练日历。

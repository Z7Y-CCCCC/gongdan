# 用户操作闭环与性能排查（2026-11-24）

## 已修复

| 链路 | 问题 | 处理 |
| --- | --- | --- |
| 生产人员登录 H5 | H5 调用了管理端登录接口，被管理端角色规则拦截 | 新增移动端密码登录接口，沿用账户锁、限流和发放会话逻辑；生产人员仍无管理端权限。 |
| 提交 → 审批 → 返工 | 移动端看不到驳回原因；替他人提交后，实际提交者看不到自己的提交；纠正提交后可能留在“已驳回”筛选 | 管理端必须填写驳回原因，防重复点击；移动端显示原因、审批人和时间，提供重新报工入口。再次提交创建新待审记录，原记录保留，页面返回未审批列表。新报工记录实际提交者，审批通知同时发给报工人和代提交者；个人产量看板仍只统计本人报工。 |
| 出入库 → 库存明细 | 缓存未命中时，先后为总数和当前页各加载一遍全量收发单、明细项及关联数据 | 数据库按工厂、类型和日期等条件计数并分页投影，只把当前页加载到 JVM。补充工厂/业务时间索引、稳定排序，以及单位改名后的缓存失效。 |
| 产品 → 库存结余查询 | 只填产品编码或名称时，没录规格的产品会被误排除 | 未填的规格条件不参与查询；按编码仍可查到该产品的库存。 |
| 报工记录与附件 | 列表逐条查附件；工单详情下载个人全部报工后再筛选；审批刷新等待附件 | 一页附件使用一次批量查询，工单履历由服务端按工单筛选，管理端审批结果不等待图片；关闭详情后丢弃迟到的图片响应。 |
| 高级报表 | Docker 反代的全局反嵌入响应头会拦截内嵌设计器；Windows 反代缺少设计器及其静态资源的转发 | 两端反代都限定在 `/ureport/` 允许同源页面内嵌；移动端和主站原有反嵌入策略保持不变。 |
| 配置与会话 | UReport 的全局属性解析器会抢先把某些配置替换成默认值；非法转发地址文本可写入会话元数据 | UReport 配置交由 Spring Boot 统一解析，保留报表属性默认值；会话 IP 只接受格式有效的 IP 字面值。 |

生产报工的进度仍只在审批通过后累计；驳回不计入工单进度。重报之前会再次校验工序及报工资格。

## 本地验证

- 后端全套 830 项通过；产品搜索补修后，27 项定向测试及 178 个 API 路由的冒烟重跑通过，没有 5xx。
- 管理端 Vitest 145 项、移动端 77 项通过；管理端生产包、H5 和微信小程序均构建成功。
- 390px H5 浏览器从未登录的报工记录链接进入，登录后看到原驳回原因；提交更正只写入一次，自动回到未审批列表，并保留原驳回记录。
- 隔离 MySQL 9.2 + Redis 运行验证了生产人员 H5 登录权限、代报工之后驳回和审批、工单进度、入出库分页、缓存刷新、报表会话和设计器 HTML。业务联调所用数据库由 Hibernate 初始化，与全量 Flyway 验收分开记录。
- 插件两套单元测试共 14 项通过；MCP 协议冒烟、Compose 配置检查 13 项、Nginx 策略测试 12 项通过。未运行生产反向代理或部署。

## 数据库与验收边界

- 发布需先备份并应用 V23、V24，再升级后端和 H5。V23 不猜测历史报工的实际提交者；旧记录仍按原报工人展示。库存明细每页最多返回 500 条，现有管理端分页兼容。
- 依赖中补齐了与现有 Flyway 相配的 MySQL 模块。隔离 MySQL 9.2 的全量迁移在历史 V15 的语法处失败；V18 也使用同类语法。本次不改历史迁移及其校验值，不改业务环境的 Flyway 历史。上线前须用部署基线 MySQL 8.4 的空库和现有备份分别验收，确认历史迁移兼容。把 Hibernate 自动更新当成生产迁移替代方案不在本次范围。
- 本地审查覆盖管理端、后端、移动端的关键流程和 API 路由冒烟；不能据此宣称所有用户操作都完成闭环。微信真机、真实短信、插件实际持久化和生产压测未验收，不对生产吞吐或响应时间提升给出未经测量的百分比。

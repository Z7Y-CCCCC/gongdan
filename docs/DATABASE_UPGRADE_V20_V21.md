# V20 / V21 数据库升级说明

本次新增迁移使用 Flyway Java migration，历史 V1–V19 SQL 保持不变。
生产目标仍是项目配置中的 MySQL 8 / InnoDB；H2 仅用于隔离回归验证。

## 升级内容

- **V20：产品版本号。** 从 JDBC 元数据确认 `products.version` 是否存在。缺列时增加
  `BIGINT NOT NULL DEFAULT 0`；已有 Hibernate 版本列时保留所有非空版本值，仅补齐空值、默认值及
  非空约束。已有有符号较小整数类型可以无损拓宽为 BIGINT；字符串、无符号或生成列等不兼容结构
  会明确失败，不会强制转换或清空业务数据。
- **V21：出入库单号按工厂唯一。** 根据索引实际列识别所有仅包含 `code` 的唯一索引，
  不依赖旧 Hibernate 的 `UK_...` 哈希名或 V1 的约束名。保留已有的 `(factory_id, code)` 唯一索引
  （字段顺序可以不同），不移除其他业务唯一约束。
- **MySQL 每张表只执行一条 ALTER。** 需要替换时，将所有旧单列唯一索引的 DROP 和复合唯一的 ADD
  放在同一条 `ALTER TABLE` 中；不会先提交删除唯一约束、再单独创建新约束。
- **H2 先建后删。** H2 的多项 ALTER 语法与 MySQL 不同，因此先成功创建复合唯一，再删除旧约束。
  元数据中的 INDEX_NAME 和 CONSTRAINT_NAME 分开处理，多个约束共用一个索引也会被完整处理。
- 两条 Java migration 均声明非事务性 DDL，并设置显式校验值。后续结构变动应增加新版本，
  不应修改已上线的 V20 / V21 或它们共用的元数据辅助逻辑。

## 适用基线与上线前检查

1. **全新数据库：** 由 Flyway 顺序执行 V1–V21。
2. **已应用 V19 的数据库：** 验证 Flyway 历史记录、备份后执行 V20 / V21。
3. **仅由 Hibernate 建表、没有 Flyway 历史的数据库：** 必须先逐项核对结构与迁移历史的等价性，
   再确定正确的显式基线。测试中的 baseline 19 仅表示“经确认已经具有 V19 等价布局”的场景，
   **不是让任何旧数据库直接跳到 19 的操作建议**。

现有生产配置的 `baseline-on-migrate=true`、默认 baseline 1 不保证可以自动接管任意 Hibernate 库。
V1–V19 中仍有非幂等 CREATE / INDEX 操作；例如 V11 直接创建 `sales_orders`。
不能为了绕过这些错误而盲目提高 baseline，否则可能跳过缺失的表、列、索引或数据迁移。
本次没有更改默认基线，也没有连接、修复或升级任何真实数据库。

上线前至少应在数据库备份/隔离恢复副本上核对：

- 当前数据库、schema 与业务表名，版本列的类型、空值及既有版本计数；
- 出入库单号的所有唯一索引，是否已有工厂级复合唯一，是否存在依赖旧单号唯一索引的外键；
- 同一工厂内重复的单号。迁移不会自动删除、合并重复业务记录；新增唯一约束遇到冲突会失败；
- MySQL 实际版本、InnoDB 引擎、字符集/排序规则与业务数据规模，并安排停止写入的维护窗口。

## 中断与重试

MySQL / H2 的 DDL 不应被当成可完整回滚的业务事务。
某张表已经迁移成功、另一张表失败时，成功部分可能保留。
两条迁移会重新读取元数据，跳过已完成步骤并保留已有版本值；可以在排除失败原因后重试。

若 Flyway 已记录失败项，应先检查实际数据库结构、确认仍满足唯一性保护，再按现有运维流程处理
失败的历史记录并重新迁移。不要盲目执行 `repair`、手工标记成功或删除业务数据；应用不会自动
改写失败的 Flyway 历史。

替代的是本次尚未发布的两份新增 SQL，并未改写 V1–V19。
曾构建过旧 V20 / V21 SQL 的工作目录需要使用干净构建，避免旧 SQL 产物与同版本 Java class 一起打包。
本次验证仅精确移除了对应的两份过期 `target/classes/db/migration/*.sql` 构建副本，未清理其他产物。

## 已完成验证

执行命令（在 `backend` 目录）：

```powershell
mvn -B -q '-Dtest=DatabaseMigrationScriptTest,SchemaUpgradeMigrationTest,DataInitializerTest' test
```

本次结果为 18 项全部通过，其中迁移相关 16 项，包括：

- 空库全部 21 个迁移、V19 升级到 V21、重复 `migrate` 无额外执行及 Flyway 校验；
- 显式旧库基线、Hibernate 风格索引名、大小写不同的 JDBC 表名、预先存在的版本列；
- 缺失版本列、空版本回填、保留既有版本值、拒绝危险类型转换；
- 多个全局唯一约束、H2 共享索引、已有复合唯一、不相关唯一索引及名称冲突；
- 同厂重复单号仍被拒绝、不同工厂允许同号；
- DDL 中途失败后 rollback / 重试，及第一张表成功而第二张表失败后的重试；
- MySQL 单条 ALTER 的 DROP + ADD 组合、旧名字转义、已有复合索引及名称冲突的 SQL 断言。

这些结果不等于已在真实 MySQL 执行升级。真实 MySQL 的锁时长、执行计划、异常恢复、数据规模与
第三方自定义外键/索引，仍须在上线前的隔离副本中确认。
